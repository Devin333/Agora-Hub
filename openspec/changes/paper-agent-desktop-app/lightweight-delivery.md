## 2. 已确定的产品边界

- Windows x64 首版交付一个完整、离线自包含的安装程序。checksum、版本说明和身份清单可以作为旁附资产，但正常安装与约定本地功能不能要求另取运行组件。
- 用户从 GitHub Releases 获取安装程序后，按常规图形界面安装并打开独立窗口；开发工具安装要求和手工命令要求均为 0。不要求克隆源码、配置 PATH、安装 Python/Node/Git/编译器或运行开发服务器。
- 下载完整安装程序后，断网仍能安装、首次启动和使用约定本地功能。不得首次偷偷运行联网 `pip`/`npm`、下载运行库或大模型；不得把缺失组件藏到第一次使用时下载。
- v1 保留单篇可提取文本 PDF 的导入、材料保存、可用文本提取与阅读，以及约定的本地资料管理、筛选、笔记、已保存成果、用户确认记忆和导出/恢复能力；不以减包为由破坏既有 owner、revision、持久化或失败反馈合同。
- v1 不默认内置本地 LLM 或 OCR 模型，不从“本地资料/记忆”推导纯离线推理承诺。远程检索和 AI 调用沿用既有显式授权、数据范围和费用边界；无模型配置不阻止本地工作区，离线不得偷偷切到远程处理。本轮不授权任何付费模型调用。
- 保留真实 Next server/BFF、Python application services 和被管理运行依赖；不把静态预览、空壳窗口、假接口或假能力状态当成正式交付。
- 不改变 Harness、Research、认证、会话、owner、质量门和业务运行路径；安装、bundle、active release 的完整性与依赖校验不削弱。

## 4. 指标定义与实测方法

### 4.1 体积与文件数

- `download_bytes`：最终分发的单个完整安装程序字节数，含 Electron 与全部必需运行组件。不能只报小型引导器或把首次下载排除在外。
- `runtime_bytes` / `runtime_files`：按现有 bundle manifest 的相同运行资源范围统计，与 1,846.0 MiB / 79,937 files 可比；仍须明确其不含 Electron 和 active release 副本。
- `managed_steady_bytes`：首次实际使用后，安装树、Electron、运行资源、active release、内部保留 payload、受管理缓存等全部副本的总占用。不能通过移到用户目录或另一个盘来隐去成本。
- `managed_peak_bytes`：安装及升级时上述资源与临时解压、staging、保留版本的峰值占用。原始下载文件单独列示；安装器另复制的副本计入峰值。
- 用户原始论文、笔记和成果单独统计，不混作软件体积；迁移/备份造成的额外用户数据副本也单独披露，不能藏在不明排除项中。
- 同时提供安装目录、运行资源、Electron、active release、缓存与临时资源分项及文件数；MiB = 2^20 bytes，GiB = 2^30 bytes。不得混用压缩大小、解压大小与稳态总占用。

### 4.2 首次、升级后与再次启动

- `install_to_usable`：安装程序开始执行到首次真实工作区可操作，包含解压、必要校验、安装准备和首次应用启动。不含下载及人为停顿，但须分别记录，不能隐去后台依赖下载。
- `launch_to_usable`：桌面启动入口被触发到真实工作区可操作，包含 launcher、准备/验证、API、前端、BFF 初始化及能力状态确认。仅窗口出现、TCP 可连、配置存在或 transport ready 均不足以单独判定完成。
- 阶段日志至少可区分宿主开始、本地准备、完整校验、API、前端、transport ready 和工作区可操作，并绑定同一 run/release 身份。上述阶段是待实现或复用的测量合同，不声称当前已齐备。
- 可操作状态由真实授权的同源请求和约定本地操作确认。验收使用隔离资料验证读写/回读，不在用户生产资料中自动写入探针数据；保留无 cookie 首次初始化回归。
- 首装首次启动、升级后首次启动、全部自有进程退出后重开、经单独授权的测试机系统重启后启动分别记录。复用常驻实例、隐藏预热或只测已有进程不算再次完整启动。
- 空库和固定的已有资料库均测量；记录文本 PDF、资料、笔记、记忆/历史成果规模，不能只用空库达标。

### 4.3 样本与环境

建议首装、升级后首次启动和获准系统冷启动各至少 3 次，完全退出后重开至少 10 次；这是待执行的工程采样计划，不是已有样本。报告全部样本、中位数、最大值及失败，不挑最好一次，不用少量样本包装可靠 P95。

记录 OS/build、CPU、RAM、磁盘实际已知信息、防护状态、电源模式、缓存状态、安装路径、库规模及构建身份。优先同机同配置比较，最低支持硬件和最终验收环境由主控后续冻结；未知磁盘类型不得猜填。不得关闭系统防护、删减功能或借助未披露开发缓存制造结果。

## 6. 有界设计方向与实施顺序

### 6.1 先证明并锁定真实运行依赖

从 v1 文本 PDF 与既有本地能力、默认配置、实际入口、动态加载和资源读取确定桌面运行 profile；记录每项保留/排除的功能依据。为 Windows 桌面运行闭包锁定版本、平台、hash、资源和许可证，不复制开发环境，不用 `dev/all` 代替发行配置。

按该 profile 重设确有必要的依赖和能力校验时，须保持确定性检查、缺失依赖失败与能力状态诚实；既不能机械保留不相关开发门禁，也不能简单删掉 `_DEFAULT_IMPORTS` 中的大包检查冒充优化。保留必要 native DLL、包数据、元数据、入口与动态依赖，不能仅凭静态 import 或一次启动裁剪。

### 6.2 真实 Next standalone 与可迁移装配

以固定 Next 版本的 standalone/tracing 产物作为运行集合候选，继续运行真实 server/BFF。官方 output 文档说明，standalone 复制追踪到的必要运行依赖并生成 `server.js`，`public` 与 `.next/static` 不自动复制；必须显式带齐，动态/原生依赖通过必要的 `outputFileTracingIncludes` 和实际运行补证。[REF-NEXT-OUTPUT]

待验证的 Windows 装配风险：若 standalone 产物包含指向构建机绝对路径的 junction，交付树将无法独立迁移。本批尚未构建 standalone 或在本项目复现这一问题；该条件性风险不能写成所有版本均会出现的通用结论。

最终分发树必须在受控构建装配中物化为普通目录和真实普通文件。构建输入的源根、目标、归属、类型与内容必须明确，未知或越界链接失败封闭；不得为了跟随 junction 任意扩大访问范围，更不得放宽既有 reparse 拒绝或完整 hash gate。必要时调整产物装配方式，而非给链接加安全豁免。

验证时将最终安装产物放到不同路径/用户目录，在没有源码树、原始 node_modules、构建机绝对路径和 PATH 开发依赖的获准隔离环境启动。覆盖静态资源、真实路由/BFF、动态/原生依赖和拒绝异常 reparse；用户不需要通过管理员权限、开发者模式或手工修链获得可迁移性。

### 6.3 先缩包，再按证据减少启动 I/O

优先收紧 Python profile 和前端生产交付集合，再重测其准备、文件枚举和校验成本。不按完整 node_modules 的包名列表直接删包，不先换 Electron，也不默认以 Electron 内部 Node 替换独立 Node。

只消除已证明重复、处于相同受控不可变输入和安全操作范围内的遍历、复制、解压及读取；保留既有完整验证覆盖、验证时点、归属、锁、失败封闭及时间/重试边界。r2 已处理的重复祖先 `lstat` 与部分重复 hash 不重复记功。

不引入跨启动的弱信任缓存，不以 size/mtime、marker、抽样或退出码代替全资源校验；不把必需准备藏到后台或第一次业务操作后再做。若必须改变 release 信任模型或业务边界，应另行评审，不能夹带于本轻量化任务。

### 6.4 安装集成、证据和后续验收

通过独立产物验证后，由相应文件 owner 集成安装配置；不得覆盖尚未整合的并行变更。

在获准非开发测试环境完成离线首装、0.1.1 升级、空库与已有库、长路径、数据保留、完整性失败和性能样本。后续实现候选运行范围匹配 gate、OpenSpec strict 与完整 smoke，结果绑定同一冻结源码、profile、锁文件、配置和资产；旧 r2 smoke 不能替新候选背书。

为拟交付 GitHub Release 资产记录单个完整安装程序的版本、Windows 架构、文件名、字节数、SHA-256、源码 commit、构建/依赖及 manifest 身份、真实签名状态和限制。checksum 是内容一致性证据，不冒充代码签名、信誉或免安全提示。准备这些记录不等于获得发布授权。
