## ADDED Requirements

### Requirement: 单个完整 Windows 离线自包含安装程序
系统 SHALL 为约定 Windows x64 环境交付单个完整安装程序，包含 Electron、被管理运行依赖、真实前后端及约定本地功能所需资源。下载安装程序后，用户 SHALL 能在断网的非开发环境完成安装、首次启动和约定本地使用；开发工具安装要求与手工命令要求 SHALL 均为 0。checksum 和说明可以单独提供，但 SHALL NOT 成为必须另取运行组件的替代品。

#### Scenario: 非开发环境离线首装
- **WHEN** 用户已取得完整安装程序，在没有项目源码、Python、Node、Git、编译器及开发缓存的约定 Windows 测试环境断网安装
- **THEN** 常规安装和桌面入口能够启动真实独立工作区
- **AND** 不要求终端命令、配置 PATH、克隆仓库或手工安装依赖
- **AND** 不通过联网 `pip`/`npm`、隐式运行库下载或大模型下载补齐缺失内容

#### Scenario: 交付产物缺少必需运行内容
- **WHEN** 安装程序必须在首次启动或第一次本地操作时另行下载必需组件才能完成约定能力
- **THEN** 该候选不满足离线自包含合同，交付验收保持未完成
- **AND** 不以较小引导器、隐藏下载、用户自行安装工具或先显示空壳窗口声称交付通过

### Requirement: 约定本地能力和远程授权语义保持不变
系统 SHALL 保留 v1 单篇可提取文本 PDF 的导入、材料保存、可用文本提取与阅读，以及既有约定的本地资料、筛选、笔记、历史成果、用户确认记忆和导出/恢复能力。系统 SHALL 保持真实 server/BFF、application service 和既有业务路径；SHALL NOT 以静态预览、假接口、伪造能力状态或默认远程替代达成轻量目标。远程检索和 AI 调用 SHALL 沿用原有显式授权、数据范围和费用合同；本补充 SHALL NOT 推导出默认内置本地 LLM/OCR 或纯离线推理承诺。

#### Scenario: 无模型配置或外网不可用
- **WHEN** 用户没有配置模型，或在断网状态下打开约定本地资料库
- **THEN** 约定本地阅读、资料、笔记和已保存成果等能力保持可用，并诚实区分缺少材料和不可用远程能力
- **AND** 不自动调用远程 AI、补发请求、下载模型或将本地操作切换为远程处理

#### Scenario: 真实服务端入口验收
- **WHEN** 在最终安装目录进行前端页面、同源 BFF、身份初始化与本地操作验收
- **THEN** 请求经过真实运行服务及既有授权/application service 边界
- **AND** 无 cookie 首次初始化能够正确完成，不用窗口出现、静态页面或假成功代替真实可操作状态

### Requirement: 桌面运行 profile 的依赖闭包与能力校验
系统 SHALL 以明确的 v1 桌面运行 profile、默认配置、真实能力和静态/动态依赖证据确定发行集合，并锁定版本、平台、hash、必要资源和许可证。系统 SHALL NOT 将开发环境或 `dev/all` extras 直接当作最小运行集合，也 SHALL NOT 按包名或文件大小直接删除依赖。既有 import 和能力门禁如需调整，SHALL 由该 profile 及实际能力证据支持，继续确定性检测必要依赖缺失和能力失败。

#### Scenario: 大型依赖仍被当前门禁或能力引用
- **WHEN** 候选拟排除当前 `_DEFAULT_IMPORTS` 检查的 `torch/scipy/numpy` 或其他大型依赖
- **THEN** 必须先提供默认能力、调用/加载路径和依赖闭包证据，并明确 profile 对应的校验合同
- **AND** 不能仅删除 import 检查、屏蔽错误或伪报能力可用来使候选通过
- **AND** 确属约定本地能力必需的依赖与资源仍须随完整安装程序交付

#### Scenario: 动态资源或原生依赖遗漏
- **WHEN** 包数据、native DLL、动态 import、入口元数据或运行文件读取不被静态分析充分覆盖
- **THEN** 候选须通过明确包含规则和真实运行证明补齐依赖
- **AND** 缺失导致能力不可用时阻断相应验收，不靠联网补装或降为伪实现通过

### Requirement: 真实且可迁移的前端运行分发树
采用 Next standalone/tracing 时，系统 SHALL 保留真实 `server.js`/server/BFF，显式装配所需 `public`、`.next/static` 及动态/原生运行资源，并对固定依赖版本执行实际运行验证。最终 Windows 分发树 SHALL 经受控装配成为普通目录和真实普通文件，不依赖构建机的绝对 target junction、符号链接、源码树或原始 node_modules。装配和迁移验证 SHALL 继续遵守既有 reparse 拒绝、路径归属、完整性和失败封闭规则。

#### Scenario: standalone 产物含构建路径链接
- **WHEN** Windows standalone 生成产生指向绝对 target 的 junction 或其他不满足交付边界的链接
- **THEN** 构建装配须在明确源根、归属、类型和内容证据下形成独立普通文件分发树，无法安全装配则失败
- **AND** 不直接打包链接，不无界跟随未知目标，不放宽 reparse gate 或将其作为例外跳过
- **AND** 不要求用户启用开发者模式、额外管理员操作或手工修链才能正常运行

#### Scenario: 脱离构建机后的迁移运行
- **WHEN** 将完整安装程序安装到不同的获准路径或用户目录，且测试环境没有源码树、构建机绝对路径和开发依赖
- **THEN** 页面资源、真实路由/BFF、动态和原生依赖仍能正常运行
- **AND** 原有身份、来源、reparse 拒绝和完整资源验证通过
- **AND** 缺少 `public`、`.next/static` 或其他必需资源不能以主页可见掩盖

### Requirement: 轻量化不削弱安全与完整依赖验证
系统 SHALL 保留既有安装、bundle、active release、release/config/dependency 身份和完整资源校验，包括适用的内容 hash、size、文件集合及类型、缺项/额外项、路径归属和失败封闭要求。系统 SHALL 保留认证、会话、owner、单实例、数据保留和业务质量门。I/O 优化 SHALL 仅消除处于相同受控不可变输入和安全操作范围内、已有证据证明的重复工作；SHALL NOT 将弱缓存或延后验证冒充等价优化。

#### Scenario: 内容或资源集合发生异常
- **WHEN** 候选存在同大小错误内容、缺项、额外/stale 文件、不可信 reparse 或依赖身份不匹配
- **THEN** 既有完整校验能够阻断安装、激活或使用中的对应受保护步骤，并保留真实失败证据
- **AND** 不用 size/mtime、旧 marker、抽样、退出码或文件数量相同替代完整验证

#### Scenario: 减少重复启动 I/O
- **WHEN** 候选合并重复枚举、读取、复制、解压或 hash 工作
- **THEN** 须证明输入稳定、归属和操作范围受控，验证覆盖及必需验证时点不变
- **AND** 不把必需校验放到宣布可用之后，也不将准备成本藏到第一次业务操作或未披露后台任务
- **AND** 跨启动信任模型或业务边界的改变不能作为本合同默认授权

### Requirement: 全链路体积与启动实测的诚实验收
系统 SHALL 对同一冻结候选记录实际完整安装程序大小、同口径运行资源大小与文件数、包含 Electron 和 active release 副本的应用稳态占用，以及安装/升级峰值占用。系统 SHALL 分别实测安装至首次可操作、首次启动、升级后首次启动、完全退出后的再次启动，并区分另行获准的系统冷启动；测量 SHALL 覆盖空库与已有库、完整准备/校验/API/前端/BFF 链路及真实本地操作。量化阈值 SHALL 仅引用 `lightweight-delivery.md` 第 5 节的待确认工程预算；未获确认或没有实测证据时 SHALL NOT 声称用户已批准或性能已达标。

#### Scenario: 记录候选包与启动样本
- **WHEN** 在获准非开发测试环境测量新候选
- **THEN** 记录全部样本、失败、环境、库规模、进程/缓存状态、阶段时间及对应源码/构建/配置/依赖身份
- **AND** 压缩安装程序、解压运行资源、Electron、active release、缓存和临时副本口径清楚，未知磁盘类型不猜填
- **AND** 不以窗口出现、端口可连、transport ready 或仅进程启动后的局部耗时替代完整工作区可操作时间

#### Scenario: 工程预算尚未确认
- **WHEN** 体积/耗时建议预算尚未获用户确认，或新候选尚未完成实测
- **THEN** 文档和交付记录明确标为建议、待确认或未实测，不宣称已签署、已达标或已验收
- **AND** 可以继续有界依赖闭包和生产产物工作，不因此自动放宽功能、安全或离线硬性要求
- **AND** 不把既有 r2 smoke、旧包体积或旧启动证据充当新候选性能证明

### Requirement: GitHub Release 资产身份与发布授权分离
拟分发的 GitHub Release 资产 SHALL 包含单个完整 Windows 安装程序，并提供可对应实物的文件名、版本、平台/架构、字节数、SHA-256、源码 commit、构建/依赖与 manifest 身份、签名实际状态和使用限制。系统 SHALL 保证记录与最终候选一致；checksum SHALL NOT 被描述为代码签名或安全信誉。文档、构建或资产记录的完成 SHALL NOT 自动授权发布、重启用户 App/系统、修改账号或覆盖其他工作。

#### Scenario: 准备候选 Release 记录
- **WHEN** 为后续 GitHub Release 准备安装程序与说明
- **THEN** 身份和 checksum 对应最终冻结实物，约定本地运行不依赖其他必需下载资产
- **AND** 保留该候选的范围检查、OpenSpec strict、完整 smoke 和实际安装/离线/性能证据状态
- **AND** 未通过或未确认项仍如实显示，其他 change 的未验收任务不被自动核销

#### Scenario: 候选构建与对外发布分离
- **WHEN** 安装程序已在本地构建和验证，但尚未取得对外发布授权
- **THEN** 保持候选及验证记录，不自动上传 GitHub Release 或推送发布标签
- **AND** 本地构建完成不自动触发用户 App/操作系统重启或账号变更
