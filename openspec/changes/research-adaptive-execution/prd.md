## 1. 一句话概述

用户只提交研究目标、材料和约束；系统自动选择完成任务所需的工作量，在既有固定业务流程内按需执行、规划、分解和委派，并由 Harness 控制预算、验收、恢复与发布。

**不向用户提供“静态 / 动态”“是否启用 planner”“是否使用多 agent”等执行模式选择。简单任务省掉不必要的规划与协调，但不省掉必需的证据、授权和质量检查。**

## 2. 背景与待解决问题

当前项目已经具备固定分析 Graph、受控动态分析阶段、AgentLoop、确定性 gate、持久事件及搜索意图理解。缺少的是把这些能力组织成自动适应任务、对用户隐藏执行策略的完整产品合同。

主要问题：

1. 当前 Graph 选择仍依赖请求选项和配置；任务的自然语言含义与实际执行反馈尚未形成自动策略闭环。
2. `GuidedIntent` 解决“搜索什么、从哪里搜索、是否需要澄清”，不等于执行任务意图、预算或分解计划。
3. 简单任务若统一经过动态 planner，会产生无必要的模型调用、等待和协调成本；复杂任务若始终沿用固定分支，又可能无法补充缺失的分析工作。
4. 一次性“简单 / 复杂”标签无法覆盖执行中的新证据，也容易混淆数据量、语义难度、信息不足与缺少能力。
5. 当前输入质量增强与动态入口存在耦合；不能通过关闭动态执行来规避本应适用的质量要求。
6. 自适应若没有可验证的触发条件、总预算、持久记录和终止规则，会把局部失败变成无限规划或绕过验收。

## 4. 产品目标与非目标

### 4.1 必须达到的目标

- **G1 统一入口**：用户不知道内部策略名称，也能得到适合任务的执行方式。
- **G2 简单任务低开销**：已知、输入完整的标准分析任务不额外调用动态 planner；直接复用既定 worker 路径。
- **G3 按需增加工作**：可在首次执行前选择更适合的合法策略，也可在执行中依据新事实申请局部升级；不要求先把完整固定流水线跑失败。
- **G4 质量不降级**：执行方式、成本偏好或发布 rollout 不得降低该请求已经确定的质量 profile、证据资格和发布条件。
- **G5 有界且可解释**：每次策略接纳、拒绝、升级和终止有可审计依据、剩余预算与持久事件；用户看到简洁原因，不看到隐藏推理。
- **G6 可验证收益**：使用固定、始终规划和自适应三种内部评测策略，在相同材料、模型和验收条件下衡量质量、调用、成本与延迟。

### 4.2 本期不做

- 不训练或在线更新专用复杂度分类器、bandit 或多 agent 架构搜索模型；不把训练数据不足伪装成已学习的 router。
- 不允许模型直接改 Graph、决定 gate 通过、扩大工具权限、发布产物、写正式 memory 或修改 active skill。
- 不把搜索意图入口改造成所有 Research 操作的通用控制器；不重写导入、解析、桌面生命周期和所有 Reader QA 路径。
- 不新增通用跨论文研究、任意网页探索或批量执行能力；仅在已有能力实际注册并通过验收的范围执行。
- 不为模型内部每个阅读、改写或思考动作创建 Graph 节点。
- 不承诺确定性 gate 能证明所有学术语义正确；语义质量通过独立评测验证。
- 不建立新的运行、预算、事件、审批、产物或评测平台；不保留未经明确需要的兼容执行层。

## 5. 用户场景与边界

| 场景 | 产品行为 | 不允许的行为 |
| --- | --- | --- |
| 已选择论文并请求标准解读 | 直接采用既定分析步骤，完成相同必需输出与 gate | 为制造“agent 感”先调用 planner 或多派子 agent |
| 请求核对同篇论文实验表与结论是否一致 | 判断既有路径是否覆盖；必要时按授权读取同论文材料、局部探索或分解核验任务 | 默认扩展到未授权论文、网站或改变用户目标 |
| 执行后发现可补足的证据缺口 | 有预算且存在已注册补证能力时，记录理由并执行受控补证/重规划 | 仅因为模型自称“困难”无限重试，或在没有证据时发布完整结论 |
| 用户只说“深入分析”，但论文与标准交付物已明确 | 保留合理默认，不询问执行模式；仅在答案确会改变范围或验收时澄清 | 反复问“选静态还是动态”“要几个 agent” |
| 论文、目标或关键约束缺失 | 请求最少必要信息；澄清轮数服从请求级上限 | 把信息不足一律判为复杂，擅自猜测论文或放宽约束 |
| 权限拒绝、预算耗尽、状态损坏、取消 | 明确暂停/终止/恢复处理，保留真实失败证据 | 借模式切换获得新权限、重置预算或重新发布 |
| 请求比较多篇论文或批量处理 | 仅当另有已验收业务入口时由该入口处理；否则说明能力边界 | 把“可生成任务列表”当作已经具备跨论文执行能力 |

用户看到的状态围绕业务事实：正在准备材料、正在分析、正在补充证据、正在核验、需要补充信息、已完成、已取消、未完成。不得把模型最终回复、工具返回成功或子任务结束直接展示为整项研究已完成。

## 6. 核心执行模型

```text
用户目标 + 已选论文 + 材料/权限范围 + 质量/资源约束
                        ↓
服务端准入：固定 Graph / policy / quality profile / capability versions
                        ↓
任务意图与初始策略候选（已知结构化请求可直接规范化）
                        ↓
Harness 校验并持久接纳合法动作
                        ↓
固定主链：source → document → RAG/evidence → analysis → VERIFY → artifacts
                                                │
                              ┌─────────────────┼─────────────────┐
                              │                 │                 │
                         既定 worker       有界 AgentLoop     受控 TaskPlan
                              └─────────────────┼─────────────────┘
                                                ↓
                            结果达标 / 可修复缺口 / 不可恢复或预算耗尽
                               ↓          ↓                 ↓
                            继续主链   申请局部补证或分解      停止/澄清
```

图中的 analysis 是产品阶段，不是新增 worker kind。实现复用现有 Graph control constructs 与准确注册的 Function、AgentLoop、Subagent / TaskPlan stage 合同。所有可到达分支和修复边界在 run 创建时已声明，运行中不替换已冻结的 Graph identity。

## 7. 功能需求

### FR-01 服务端自动接纳，不提供用户模式开关

- 正式用户入口不展示或要求提交内部执行策略、planner 开关、agent 数量或具体 worker/model 绑定。
- 服务端依已发布的能力/profile 和请求身份接纳统一分析运行；是否启用自适应 release 由部署资格控制，不由单次用户请求开启。
- 对外部注入的 `dynamic_analysis`、`dynamic_task_plan`、策略覆盖或内部 policy/binding 字段明确拒绝并提供可理解的错误；不静默接受或建立永久兼容别名。
- 明确的任务预算/时限是资源约束，不是权限授权，也不是“复杂模式”入口。

### FR-02 执行任务意图与当前能力对齐

- 候选至少表达 `task_kind`、`paper_ref`、`deliverables`、`constraints`、`input_refs`、`missing_inputs` 与有限的 `proposed_action`；这些是设计合同字段，不表示当前已有同名生产 schema。
- 模型只提供语义和动作候选；真实来源修订、可用能力、授权、总预算和 exact bindings 由服务端解析。
- 不仅依据字数、文献数量、用户使用“深入”或模型自报 confidence 判定需要动态规划。
- 输入不明确、执行成本高、固定模板不匹配与能力缺失必须区分；缺少能力不能转成“多开 agent”。
- 搜索意图可作为有血缘的上游信息，但不得直接充当已接纳执行计划。

### FR-03 低开销初始执行

- 已知结构化分析请求由普通函数生成规范化任务与固定执行候选，不新增意图分类或 planner LLM 调用。
- 需要理解自然语言约束时，使用一次有界结构化候选过程；避免先调用一个“复杂度打分 agent”，再调用另一个 agent 重复理解相同目标。
- 固定路径复用原业务 worker 和必需输出角色；“直接执行”不意味着省略原先必要的模型分析、RAG、gate 或发布检查。
- 如果证据已表明存在独立子目标或必要的探索，允许直接申请合法的 loop / TaskPlan，不强迫先完整执行另一条路线。

### FR-04 按需规划、分解和委派

- 模型可申请继续当前任务、同论文范围补证、分解分析、委派已注册能力或请求必要澄清；不得直接指定全局下一个 Graph 节点或自授权限。
- 单个明确子目标内的探索优先在受限 worker/AgentLoop 中完成；只有需要独立输入输出、验收、并行或恢复的业务任务才进入 TaskPlan。
- Harness 必须验证候选 schema、能力、依赖、输出角色、输入 ref、授权、资源及版本，持久接纳后才派发；拒绝必须留下原因。
- 复用 `analysis.structure`、`analysis.contribution`、`analysis.experiments` 的必要输出合同，不因省成本丢失角色。
- 多 agent 不是复杂任务默认值；没有独立收益或合格并行能力时不得增加 fan-out。

### FR-05 根据执行反馈局部升级

- 触发依据来自已接纳的结构化执行结果、证据覆盖/引用检查、已声明 gate 或 capability precondition；模型自评、界面进度、todo 状态或日志文本本身没有路由权。
- 允许修复的情况包括同论文可补足的证据缺口、可重建的候选输出和依赖证据支持的细化需求；必须关联可执行修复能力与具体 observation ref。
- 权限拒绝、未知/损坏状态、schema/identity 篡改、不可用能力、取消及预算耗尽不得升级为“更复杂模式”以继续。
- 不对同一失败指纹在没有新证据时重复升级；失败指纹至少绑定目标、gate、输入修订和已尝试修复类别。
- 已接纳、仍有效的来源编译/证据结果可以按既有 ref authority 复用；不把一次补证变成无条件重跑整个 run。
- 支持已经声明且有预算的局部重规划，但不能用切换策略重置 attempt、replan、turn 或成本账本。

### FR-06 Graph、质量与发布不可被策略改变

- 每次运行冻结 Graph/version/checksum、policy identity/version、允许的执行策略与模型/能力 binding 集合、质量 profile 和授权范围。具体执行策略与 plan revision 可以在该集合及已声明边界内有界调整，须先持久接纳；恢复时重放已有决定，不重写冻结合同。
- 固定步骤仍遵循 source collection → evidence → agent analysis → report/reader candidate → quality gate → artifacts/storage。
- 所有策略满足同一请求的质量 profile；输入合同与高价值 claim 证据资格不得依赖用户是否选择动态模式。
- 补充证据只能形成有来源、修订、权限和校验信息的新候选/已接纳 ref，不原地篡改已有 evidence checksum 或把模型推测标成已核验事实。
- 策略、todo、子任务成功不等于总体成功；只有顶层必需输出与 gate 通过、终端授权满足，才可发布。
- 失败期间允许依既有规则保存隔离的诊断候选，但不得进入正式报告/产物目录或被误标为合格报告。

### FR-07 请求级总预算与终止

- 所有语义理解、planner、worker、工具、检索、子 agent、重试、compaction 和恢复后调用使用同一请求 lineage 下的权威预算。
- 至少约束 `max_turns`、`max_replans`、`max_worker_calls`、任务/并行数、token 与 wall-clock 上限；使用既有计量和预留 owner，不另建 ledger。
- provider 重试、失败调用和已发生但结果不明的调用不可被排除在消费或保守预留之外。
- 子任务只获得父预算的受控分配；派发前原子预留，终止后按权威事实结算。
- 无法精确计量或确认副作用时按既有 indeterminate / quarantine 规则失败封闭，不以恢复为名盲目重发。
- 澄清也必须有请求级上限；用户改变目标/材料或明确批准扩大预算时形成可追溯的新 revision/授权，而不是静默续费或重置。

### FR-08 可观测性与用户控制

- 记录候选来源、接纳动作、reason codes、关联输入/观察、policy ref、Graph identity、预算前后值、attempt/plan revision 和结果 refs。
- 策略接纳及升级事件必须先于对应派发持久提交；使用现有 canonical event / transcript，不另起平行状态机。
- 用户可以查看业务进度、简洁升级原因、已消耗资源、缺口与停止原因，并使用既有取消与必要授权流程。
- 不展示 chain-of-thought、原始私有上下文、凭据或其他任务的材料；理由是可审计事实摘要，不是隐藏推理记录。
- 不在已知材料和标准交付物足够时重复澄清，不把选择技术策略转嫁给用户。

### FR-09 持久恢复与幂等

- 重启后恢复原策略接纳、计划、预算、结果和 pending child 状态，不重新“猜一次复杂度”。
- 重复事件、重复提交和子任务完成乱序不能导致重复规划、重复发布、重复释放额度或改变聚合结果。
- 已接受的决定不会因最新模型回答、policy 默认值或当前代码主分支变化而被重新解释。
- 对不可恢复的版本/能力缺失显示明确状态，不能回退到无门、无隔离或新 Graph 的隐藏替代执行。

### FR-10 受控配置与部署

- 只有验收合格的 task/quality/model/capability profile 能进入自动接纳集合。
- 普通运行不得更新 active policy、阈值、模型路由器或 skill；经验只进入已授权的观察/评测或 memory 流程。
- rollout 可以限制租户与任务范围；关闭自适应只影响新准入，活动 run 按原合同完成、取消或终止。
- 明确选择并验收的 serial adapter 是一种已声明执行资格，不是静默并行降级；真正需要缺失能力的任务必须说明无法执行。

## 8. 与现有变更的关系及优先级

| 既有 owner | 本变更的边界 |
| --- | --- |
| `harness-runtime-execution-and-parallel-agent-orchestration` | 继续拥有 execution safety、子任务生命周期、事件和并行恢复；其适用发布门未通过时，不启用相应自适应能力。动态默认关闭属于部署资格，不是要求终端用户逐题选模式 |
| `research-evidence-context-quality-foundation` | 继续拥有输入/证据资格及评测基础。其进度观察不能自动成为路由信号；本变更只使用经过验证的结果与 gate 事实，并在合格 profile 内解除质量与执行模式耦合 |
| `research-local-desktop-readiness` | 继续拥有 request admission、运行状态、durable storage 与本地恢复；本变更复用其入口及 projection |
| `paper-agent-desktop-app` | 继续拥有桌面壳、设置与生命周期；本变更不重做 shell，只提供无模式选择的分析请求和可解释状态 |
| canonical `research-dynamic-analysis-stage` | 更新显式 caller opt-in 的产品选择合同；冻结 Graph、固定 stage、必需角色、隔离与发布约束继续有效 |

在本变更的 release 证据未通过前，现有默认行为保持不变。不得把 PRD 合并、默认开关存在或 spec 校验通过当作实现/发布验收。

## 9. 验收与评测

### 9.1 必须覆盖的可执行验收场景

| ID | Given / When | Then |
| --- | --- | --- |
| AC-01 | 已知、完整的标准分析请求进入合格 profile | 无用户模式参数；零新增动态 planner 调用；保持必要角色、gate 与结果合同 |
| AC-02 | 语义候选表明需要同论文多轮核验，且能力与预算均具备 | Harness 可在首次完整分析前接纳适当策略；不强制先浪费一次全量固定执行 |
| AC-03 | 执行后出现可补足的缺证事实 | 记录 observation 与理由，预算内补证/重规划，并重新经过适用 gate |
| AC-04 | 模型输出“已完成”，但证据/角色/gate 不满足 | 不发布；按合法修复或停止路径处理 |
| AC-05 | 模型建议跳 gate、扩大来源、改变质量、选择未注册 worker | 接纳前拒绝，零越权派发，保留拒绝证据 |
| AC-06 | 请求注入内部策略字段或要求绕过权限 | 明确拒绝；不得控制 Graph / worker / policy |
| AC-07 | 输入不明或所需能力不存在 | 只澄清有用信息或说明限制；不伪装成动态执行成功 |
| AC-08 | 切换策略、递归子任务或 provider 重试将耗尽总预算 | 不获得新预算；不会产生超限的新派发，正确保留已发生消费 |
| AC-09 | 同失败指纹无新证据再次要求升级 | 受控拒绝/终止，不形成无收益循环 |
| AC-10 | 接纳后、派发后、结果落盘后或发布提交前发生 crash | 从冻结身份与持久事实恢复；不重复派发已确认动作或发布 |
| AC-11 | 子任务乱序完成、重复事件、取消/超时与完成并发 | 聚合和终端状态保持确定性；无重复结算或隐藏后台执行 |
| AC-12 | 固定、loop、TaskPlan 处理同一质量 profile | 使用相同资格要求；不会因策略较便宜而少检查必要条件 |
| AC-13 | 关闭 rollout 或依赖能力失去资格 | 阻止新准入；活动 run 不换 Graph 或降低门，按既有规则安全收束 |
| AC-14 | 文档中含提示注入或其他租户 ref | 不扩大能力/数据范围；原始私有上下文不进入未授权候选、事件或子任务 |

### 9.2 评测方法

- 复用现有 Research evaluation tooling 与产物格式，不建立新 benchmark 平台。
- 比较三种**内部评测策略**：既定分析、始终进行动态规划、自适应；测试开关不得成为正式用户参数。
- 冻结任务、paper/source revision、模型/工具版本、quality profile、预算和价格口径；按论文来源分组划分训练/开发/留出集合，避免同源泄漏。
- 样本必须包含固定路径足够、需要补充工作、需要澄清/拒绝三类，以及失败、权限、预算、恢复与对抗样例；类别不能由待评估 router 自己标注。
- 真实模型结果使用配对重复试验，报告方差/置信区间和完整失败分母；确定性 fake 测试只证明控制合同，不证明语义能力。
- 语义质量使用独立参考证据和冻结 rubric；模型自评、计划完成率、schema 通过率不能代替业务质量。关键门仍由 deterministic gate 控制。
- 统计全部解释/路由/planner/worker/重试/工具开销；无可信价格时只报告 token、调用、检索与时间，不宣称已节省货币成本。
- 样本量、非劣检验方法和统计单位在 pilot 后、正式留出运行前冻结；证据不足即保持未验收，不能事后降低阈值或删除困难样本。

### 9.3 首版发布目标（提出的目标，不是已测结果）

| 指标 | 发布门 |
| --- | --- |
| 安全与控制合同 | AC-01 至 AC-14 适用的确定性场景全部通过；零授权/gate/预算/发布边界绕过 |
| 标准请求规划开销 | 已知结构化任务零新增语义分类/动态 planner 调用；固定路径不会为自适应额外 spawn 子 agent |
| 关键质量案例 | 预先冻结的关键案例零新增错误发布、证据丢失或必须角色缺失 |
| 留出语义质量 | 对同质量 profile 的始终规划基线，任务质量通过率差的 95% 配对置信区间下界不低于 -2 个百分点；这是统计非劣界限，不是降低 gate |
| 需要补充工作的任务 | 相对既定分析基线的质量通过率差，其 95% 配对置信区间下界不低于 0；同时必须展示真实的“基线未完成、自适应合格完成”案例 |
| 混合任务工作量 | 在满足质量门前提下，相对始终规划基线，计入路由/重试的平均模型 token 至少下降 15%；货币成本仅在价格版本可靠时另行比较 |
| 标准任务延迟 | 同环境、同材料状态下的服务端 active-time p95 不高于既定路径的 1.15 倍；冷启动与人工等待单列，不能选择性排除失败 |
| 恢复/回滚 | exact identity replay、重复投递、取消、crash 与 rollout 回滚证据齐全，活动 run 不被重新路由 |

上述目标可以在正式留出评测前通过受审查的 PRD/阈值版本变更调整；不得在看到正式结果后为了通过而降低标准。通过单个指标不代表可以替代其他门。

## 10. 分阶段交付

1. **合同与基线**：冻结能力范围、输入/输出角色、quality profile、策略候选、原因码、预算与评测协议；明确依赖实际验收状态。
2. **统一准入与低开销路径**：接入执行意图候选、无模式用户入口和已有固定 worker；首先证明标准任务没有额外 planner 开销和质量回退。
3. **受控自适应**：接通同论文 bounded loop / TaskPlan、初始适配选择和反馈修复；所有分支 exact 注册并进入现有持久控制面。
4. **恢复、交互与故障验收**：覆盖依赖不可用、重复失败、取消、预算和重启，提供真实业务状态与解释。
5. **评测、灰度和收束**：完成留出评测、受控 live 证据及回滚；只有满足依赖与本 PRD 发布门后才能开放合格 scope。

本期不是先上线一个不受控的“智能路由 demo”再补门；每个上线 scope 都必须形成完整产品闭环。未完成范围不伪装为可用能力。

## 11. 风险与处理

- **模型低估任务所需工作**：保留执行反馈后的局部修复；不得只依赖入口分类。
- **模型过度规划**：已知请求走无额外 planner 的固定路径，记录规划边际收益与完整成本。
- **模型自评假成功**：模型只生成候选，必需输出、证据及发布资格独立验证；语义不足通过评测暴露。
- **Graph 过细或出现第二套控制器**：只编排业务边界，重用现有 Choice/Loop/Repair、TaskPlan 和 AgentLoop owner。
- **补证导致上下文污染或陈旧结果复用**：所有新 refs 校验权限、修订、校验和及血缘；不静默覆盖已接受事实。
- **配置降级绕过验收**：缺失能力明确 unavailable；回滚不能关闭质量门或扩大兼容执行范围。
- **和活跃变更相互覆盖**：保持各 owner，引用其发布证据，不改写其任务完成状态；集成前重新核对真实源码。

## 12. 研究依据与结论边界

参考依据详见 `evidence/research-basis.md`。核心采用：工具按需规划/委派、有限合法策略选择、执行不足时的有界分解，以及质量—成本联合评测。

不照搬：ADaPT 的 LLM 自评完成、Adaptive-RAG 的无证据直接回答路线、MasRouter 的训练后效果假设、把 todo 当可调度计划、把任意 prompt 视为控制指令。

**本 PRD 的结论是让 agent 提出“下一步需要做多少工作”，让 Harness 决定“哪些工作允许执行、何时结束、何时可以发布”。用户不承担技术策略选择，系统也不放弃可验证的控制边界。**
